* Synopsis
:PROPERTIES:
:CUSTOM_ID: summary
:END:

** Outcome
- The Homebrew cask's GUI app has a *trusted Developer ID signature* and *stapled notarization ticket*.
** Before
- The release script *re-signs the app ad hoc* and publishes a DMG without notarization.
** After
- The release app and DMG are *notarized and stapled* before publication.
- *Failed signing or notarization prevents publication* and a cask update.
** Changes
- Release signing uses the *Developer ID Application certificate* for Tadg Paul Ltd, team =2H98A242M4=.
- Release builds enable the *hardened runtime* and exclude debugging entitlements.
** Unchanged
- The *CLI release path*, bundled-resource exclusions, model-sharing contract, and cask installation name remain unchanged.
** Edge cases
:PROPERTIES:
:CUSTOM_ID: synopsis-edge-cases
:END:
- A *missing certificate or notarization profile* stops the release before GitHub upload or cask changes.
- A *rejected notarization* retains its diagnostic identifier and stops publication.
** Decisions
- Xcode *signs nested code*; the release script does not re-sign the outer app with =--deep=.
- The app and final DMG each receive a *notary submission* so both tickets can be stapled.
** Next step
- Definition review and operator sign-off precede implementation under [[#delivery-handoff][Delivery Handoff]].

* Context
:PROPERTIES:
:CUSTOM_ID: context
:END:

** Problem
- A GUI app installed from the Homebrew cask is reported as unsafe by macOS. The current release script explicitly applies an ad hoc signature and has no notary submission. The installed copy has not been examined, so the precise Gatekeeper assessment remains unverified.
** Outcome
- A fresh cask download carries an app and DMG whose Developer ID signatures and stapled tickets can be verified locally, then receives human first-launch validation.
** Scope
*** In scope
- GUI Release build signing, hardened runtime, notarization, stapling, verification, publication ordering, and release documentation.
*** Out of scope
- Publishing a release during implementation, changing the separate tap repository, changing the CLI release, or managing Apple account credentials.
*** Unchanged
- Existing bundle inspection and resource exclusions precede packaging; the cask continues to install =Superscale.app=.

- Project profile :: [[file:../../.sdlc/project.yaml][Project profile]]
- Product authority :: [[file:../../README.md][README release target]] and [[file:../../docs/RELEASE_CHECKLIST.md][Release checklist]]
- Architecture authority :: [[file:../../docs/ARCHITECTURE.md][Application architecture]]

- External contract :: [[https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution][Apple notarization requirements]] and [[https://developer.apple.com/documentation/security/customizing-the-notarization-workflow][Apple notarytool workflow]].
** Constraints and dependencies
:PROPERTIES:
:CUSTOM_ID: constraints-and-dependencies
:END:
- The signing identity is =Developer ID Application: Tadg Paul Ltd (2H98A242M4)=; its team ID matches the Xcode project's =DEVELOPMENT_TEAM= setting.
- A locally stored =notarytool= keychain profile is required. Secrets and credentials remain outside the repository and logs.
- Apple notarization is an external, potentially metered operation and is verified only as a bounded one-off, never in =make test= or a persistent build check.
- The existing shell script exceeds the shell standard's complexity threshold and already integrates Xcode, GitHub, and the tap. Retain the existing release entry point for this bounded change; isolate candidate preparation and validation in one small helper so publication remains visibly downstream.
** Decisions
- The app target's Release configuration uses manual signing with =CODE_SIGN_IDENTITY= set to =Developer ID Application: Tadg Paul Ltd (2H98A242M4)=, =DEVELOPMENT_TEAM= set to =2H98A242M4=, =ENABLE_HARDENED_RUNTIME= set to =YES=, =OTHER_CODE_SIGN_FLAGS= including =--timestamp=, and =CODE_SIGN_INJECT_BASE_ENTITLEMENTS= set to =NO=. The Debug configuration and UI-test target are unchanged. Any hardened-runtime exception requires a separate authorized requirement.
- The script verifies Xcode's app signature and does not overwrite it with an ad hoc or deep signature.
- Notarize a ZIP containing the signed app, staple and validate the app, then build the DMG. Notarize, staple, and validate the final DMG before hashing or uploading it.
- Use a named keychain profile for =notarytool=; do not pass passwords or API private keys on the command line or commit them. The first =notarytool submit= checks profile usability; there is no separate profile preflight that contacts Apple.
** Unresolved blockers
- None for definition. Delivery must verify the certificate and local notary profile before a live one-off submission.

:PROPERTIES:
:CUSTOM_ID: ot-153-2

- Procedure :: Submit one app ZIP and one final DMG using the keychain profile and =--wait=; require accepted status; staple and validate the app before DMG packaging, then staple and validate the DMG; assess the app with =spctl=.

:CUSTOM_ID: ot-153-3

* Solution Design
:PROPERTIES:
:CUSTOM_ID: solution-design
:END:

** Architecture context
- Relevant components :: The Xcode target produces the GUI bundle; =scripts/release-gui.sh= inspects, packages, uploads, and updates the local and tap cask.
- Ownership boundary :: This repository owns the app and its release script. Apple owns certificate trust and notarization; the external tap repository is updated only by an authorized release invocation.
** High-level design
- Configure only the app target's Release signing as stated under Context / Decisions. Keep Debug development signing and the UI-test target intact; do not add hardened-runtime exception entitlements.
- Before building, check the required local signing identity without printing secrets. Let the first notary submission establish keychain-profile usability.
- After building and resource inspection, verify the Xcode-produced signature and entitlements. Package the app in a temporary ZIP, submit once with =notarytool --wait=, require acceptance, then staple and validate the app.
- Copy the stapled app to DMG staging; create the DMG, sign it with the Developer ID identity using =--timestamp= and a distinct =com.tadgpaul.superscale.dmg= identifier, and verify the signature. Submit it once, require acceptance, staple and validate it. Calculate SHA-256 only after stapling, since stapling changes the DMG bytes.
- Run GitHub upload and cask generation only after every prior check succeeds. Keep temporary files in OS-allocated directories and clean only the exact temporary paths created by this invocation.
- The candidate-preparation helper accepts an app path and an output DMG path, and owns signing verification, notarization, stapling, and the final DMG. It exposes a status-check operation for =notarytool= JSON output so an =Invalid= result can be checked locally. =release-gui.sh= calls the helper and enters its existing GitHub and cask phase only on success. Do not run the publishing phase during implementation verification.
** Design decisions and verification
- Decision :: Use Xcode target signing instead of =codesign --force --deep= on the finished app.
- Rationale :: Xcode signs nested code inside out, while post-build deep signing can mask incorrect nested signatures.
- Verification :: [[#ot-153-1][OT153.1 - Inspect release signature]] and implementation review of the Release build settings.
- Decision :: Submit the app ZIP and DMG separately.
- Rationale :: The app must be stapled before it is sealed inside the read-only DMG; the final DMG must also be stapled before hashing.
- Verification :: [[#ot-153-2][OT153.2 - Notarize and validate candidates]].
- Decision :: Sign the DMG with the same Developer ID identity and a separate identifier before its notary submission.
- Verification :: [[#ot-153-1][OT153.1 - Inspect release signature]].
** Routine details left to implementation
- Use the existing script's conventions for output and temporary paths; choose a fixed, documented keychain profile name.
** Architecture impact
*** Security impact
- Threat boundary :: The release changes from an ad hoc local signature to an Apple-verifiable Developer ID and notary ticket.
- Data and secrets :: The private signing key and notary credentials stay in Keychain; no secret values enter the repository, command output, or release artefacts.
- Access :: Signing and notarization use the local authorized developer account; GitHub and tap write access is unchanged.
- Conclusion :: Publication must fail closed if signing or notarization cannot be established.
